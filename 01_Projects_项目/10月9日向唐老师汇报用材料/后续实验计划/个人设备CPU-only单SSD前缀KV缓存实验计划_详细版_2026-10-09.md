# 个人设备 CPU-only 单 SSD 前缀 KV 缓存实验计划

编制日期：2026 年 10 月 9 日。版本：v1.0，待执行方案。

本计划用于明确实验环节、所需材料、比较方法、验收条件和结果交付，不展开逐条安装命令与操作教程。具体接口实现、环境安装、数据处理和计时方法，在各阶段执行前分别细化。

## 1 研究目标和完成范围

本研究使用个人笔记本，在 CPU 执行推理、RAM 保存活动与历史状态、单块本地 SSD 保存历史状态的条件下，验证相同 token 前缀的精确 KV 复用是否能够降低交互请求延迟。在确认恢复正确且存在收益空间后，研究恢复与重算的选择，以及后台保存历史 KV 对前台推理的影响。

最终至少形成三项成果：可复现的单设备原型；不同长度、缓存状态与负载下的恢复和重算收益边界；基线与候选策略的公平比较。实验允许得出 SSD 恢复不适合某些条件、固定规则已经足够、候选策略没有稳定增益等结论。

当前设备信息已在本次会话中只读检查：AMD Ryzen 7 8845HS，8 个物理核心、16 个逻辑处理器；操作系统可见内存约 31.26 GiB，即标称约 32 GB；一块 YMTC PC41Q-1TB-B SSD，系统报告容量约 954 GiB；检查时 D 盘剩余约 434.6 GiB。空闲空间、系统负载及软件版本在正式执行前重新记录。

研究表述统一为“借鉴 HiCache 机制的 CPU 端侧前缀缓存原型”。本计划采用 llama.cpp 的状态能力，并不据此声称已经移植原版 SGLang HiCache。个人电脑测量可验证机制，不直接代表手机、工控机或 NPU 的性能。

### 1.1 首轮纳入范围

- 同一模型、同一模型文件、兼容执行配置下的连续相同 token 前缀。
- 文档在前、问题在后的重复问答与多文档交替访问。
- 活动 KV、历史前缀、状态文件、读取与写出缓冲的资源管理。
- RAM 复用、文件恢复、完整重算，以及可测量的等待决策。
- 前台请求与本地读写竞争，历史缓存容量受限的情况。

### 1.2 后续再研究的内容

KV 量化、稀疏注意力、权重卸载、GPU/NPU 执行、跨设备传输、复杂未来访问预测、按页流式恢复、完整 P/D 分离均不作为首轮完成条件。同前缀在途加载合并可在单设备主线完成后补充。

## 2 研究问题与可否定假设

| 编号 | 问题或假设 | 必要证据 | 不成立时的处理 |
|---|---|---|---|
| R0 | 状态导出和恢复能够正确继续推理 | 同输入位置 logits、多步固定 token 延续与失败回退验证 | 修正实现或更换后端，暂停性能结论 |
| H1 | 恢复与重算的优选路径随长度或负载变化 | 真实恢复、完整请求 TTFT 与重算的配对比较 | 若始终同一路径更优，采用简单规则并限定结论范围 |
| H2 | 轻量成本判断可减少错误选择或等待 | 对比经过独立调参的固定规则，同时计入决策开销 | 若收益不足，保留最佳固定策略 |
| H3 | 控制后台写入能够缓解前台干扰 | 延迟、生成间隔、写入积压和后续复用联合评价 | 若没有竞争或代价抵消收益，不宣称写入优化有效 |
| H4 | 收益受到历史工作集和缓存预算影响 | 容量充足与容量受限的相同轨迹比较 | 记录收益出现的预算及工作集范围 |

优先级为 R0、H1、H4，再根据结果进入 H2、H3。H2 与 H3 不预设必然成立。

## 3 设备和软件准备

### 3.1 硬件与运行环境材料

| 材料 | 需要记录的内容 | 用途 |
|---|---|---|
| 个人笔记本 | CPU、核心数、RAM、SSD、固件与系统版本 | 确定结论适用范围 |
| 电源与散热条件 | 插电状态、电源模式、散热模式、温度、频率 | 控制移动处理器功耗与降频变化 |
| 存储环境 | 分区、文件系统、剩余空间、状态目录位置 | 解释文件恢复与竞争路径 |
| 后台负载记录 | CPU、内存、磁盘活动和明显后台任务 | 定位异常测量 |
| 软件工具链 | 编译器、构建参数、后端提交、运行库 | 复现实现和性能 |

主环境先使用 Windows 原生，避免为第一阶段打通接口增加系统迁移成本。正式冷态测量若在 Windows 上无法得到可靠证据，可另建立 Linux 原生复现实验；不同系统的结果分别报告。WSL 的文件系统与虚拟磁盘路径存在额外因素，应作为单独环境，不能与 Windows 原生或 Linux 原生混合。

CPU-only 由实际执行后端确认。处理器带集成显卡，但实验禁用 GPU/NPU 卸载；不能仅凭设备名称判断执行路径。模型权重在测量前加载与预热，记录实验期间是否发生权重缺页、系统分页或内存压缩干扰。

C、D 分区属于同一块 SSD，共享硬件资源。将读写放在不同分区不能构成双磁盘隔离实验。

### 3.2 后端与开发材料

选择 llama.cpp 官方源码，冻结一个通过接口验证的提交版本。准备 CPU 构建、序列状态导出/导入与文件保存/恢复接口、tokenizer、logits 读取接口和单调高精度计时工具。正式实现可使用 C/C++ 控制关键路径，Python 用于负载生成、日志处理与结果整理；若采用 Python 绑定，须确认其确实暴露所需接口并与后端版本一致。

首轮需要的程序模块包括：

| 模块 | 职责与约束 |
|---|---|
| 模型执行器 | 长期保留模型，运行 Prefill/Decode，记录实际处理 token |
| 请求构造与分词模块 | 固定模板，验证完整输入的最长公共 token 前缀 |
| 前缀索引 | 记录缓存键、可复用长度、位置、版本、状态和对象大小 |
| RAM 历史缓存管理器 | 执行预算与统一淘汰规则，正确计量常驻状态及副本 |
| 状态存储模块 | 保存、校验、恢复与失败回退，写完成后发布对象 |
| 策略模块 | 统一实现重算、恢复、等待及成本选择 |
| 后台写入管理器 | 限制任务、在途字节、源对象引用和积压 |
| 请求回放器 | 使用固定请求列表、到达时间、随机种子及并发设置 |
| 测量模块 | 记录事件时间、logits、内存、I/O 和错误 |
| 分析模块 | 生成汇总表、区间估计和研究图表，保留原始日志 |

前缀索引第一版可用完整前缀 token 序列与配置哈希关联对象，不要求先实现完整 HiRadixTree。状态结构与缓存键正确性优先于复杂索引。

## 4 模型与统一推理配置

### 4.1 模型选择

| 用途 | 模型 | 权重形式 | 验收后进入的阶段 |
|---|---|---|---|
| 调试与接口验证 | Qwen3-0.6B | 官方 GGUF，Q8_0 | 正确性、日志和计时打通 |
| 主要实验 | Qwen3-1.7B | 官方 GGUF，Q8_0 | 读算边界、容量和策略实验 |
| 泛化补充 | Qwen3-0.6B 的代表配置 | 保持同一权重形式 | 检查模型变化是否改变结论 |

两个模型分开统计。Q8_0 是权重配置，初版 K/V 固定 FP16，不把权重量化与 KV 量化混为一个变量。模型下载后记录精确文件名、来源版本、哈希和磁盘大小；不只记录模型名称。选择较大模型或其他量化精度属于后续扩展。

### 4.2 初始运行配置

| 项目 | 起步设置 | 说明 |
|---|---|---|
| 推理设备 | CPU，GPU 卸载为 0 | 检查实际后端与日志 |
| 线程 | 先测 4、8、16，随后冻结 | Prefill 和 Decode 线程配置均记录 |
| 上下文容量 | 8192 token | 总输入与输出不能超过容量，初版禁用隐式滑动 |
| KV 精度 | K、V 均 FP16 | 恢复与重算必须一致 |
| 思考模式 | 关闭 | 确认模板实际生成的 token，避免隐藏长思考 |
| 输出 | 上限 64 token | 提前 EOS 记录实际长度，不伪造固定长度 |
| 并发 | 单请求开始 | 并发 2 仅用于代表配置 |
| 模型加载 | 测量前完成并预热 | 应用冷启动另列，不混入常驻服务结果 |
| batch/ubatch、注意力实现 | 校准后冻结 | 记录配置，保证各组一致 |

正确性主要使用固定后续 token 的 logits 比较。贪心输出作为辅助一致性检查，不用于宣称模型推荐采样下的任务得分。真实回答质量评估采用统一、预先确定的非思考采样配置与种子，并单列结果。

## 5 数据、提示和请求轨迹

### 5.1 数据材料

采用可控数据与公开文档两部分。可控数据用于准确改变 token 长度、重复机会和工作集；公开文档用于检查结论是否只在人工文本上出现。

| 数据 | 材料与规模 | 用途 |
|---|---|---|
| 调试样例 | 1—2 份短文档，每份多个不同问题 | 状态恢复和缓存键测试 |
| 可控前缀 | 256、1024、2048、4096 token 的实际输入前缀 | 单请求微基准 |
| 中文公开文档 | LongBench v1 的 multifieldqa_zh | 中文代表负载 |
| 英文公开文档 | LongBench v1 的 qasper | 英文代表负载 |
| 初始请求集合 | 20 份不同文档，每份约 5 个请求 | 校准与首轮回放 |
| 扩展请求集合 | 容量实验需要的更多不同前缀 | 不足以形成目标工作集时扩充 |

20 份文档是初始规模，不是所有配置的强制上限。某些子集并非每份文档提供五个问题：能按相同 context 合并的先合并，不足时添加人工可核对的问题或明确记录的合成问题。数据清单注明原始、改写或新增来源。

### 5.2 提示结构和 token 边界

固定结构为“系统提示＋文档＋固定分隔符＋本次问题＋回答起始标记”。保存对象截止到共同分隔符，不包含特定问题。以最终模板化的完整请求分词为准，核对连续共同 token，而不是先分别分词各文本片段再假定可以拼接。

关闭思考模式的设置、特殊 token、BOS/EOS、换行、文档序号等都可能改变前缀，应纳入版本记录。文档 ID 如果写进输入，位置与内容固定；用于实验管理的 request_id 不应无意插入共同前缀。

精确长度微基准通过 token 层面控制；真实文本请求记录实际长度，不为凑长度破坏语义。若截短公开文档，应确保需要验证的答案仍可找到，否则该样本只用于系统性能，不用于答案质量。不得把修改后负载的结果表述为标准 LongBench 排行榜成绩。

### 5.3 校准与测试划分

初始按文档划分 5 份校准、15 份测试，并分别覆盖中文和英文。保存 split 清单，排除重复 context 及明显近重复文档。校准集用于线程选择、超时、成本估计器、误差裕量、预算及压力档位。正式测试集不参与调参。

测试轨迹使用预先冻结的随机种子。在线更新只能使用当时已经完成的请求测量，不读取未来路径耗时或未来访问。模型/接口调试样例单列，不进入最终性能统计。

### 5.4 请求机会、命中与工作集

分别记录三种量：安排为重复访问的请求比例；实际缓存命中请求与 token 数；已就绪并真正用于推理的 token 数。安排 50% 重复机会不保证 50% 命中。

工作集按不同历史缓存对象实际字节量计算；共享系统提示或重复 token 不能机械重复计数。初版若按完整对象保存而没有共享存储，明确说明重复公共部分会重复占用空间，所有策略保持同样对象布局。

## 6 内存、磁盘预算与状态生命周期

### 6.1 两类预算

设置历史缓存目标预算 B_hist，初始扫描 256 MiB、512 MiB、1 GiB。另设置统一的缓存子系统内存上限，覆盖历史状态、读取暂存、写出源副本和管理元数据。模型权重、活动上下文、执行工作区单独计量，但整体峰值内存必须报告。

有的后端按上下文容量预分配 KV 池，逻辑淘汰不一定降低进程占用。必须区分逻辑有效 KV 字节、预分配池、独立历史对象和临时副本。不能删除索引后仍把对象留在隐藏列表，也不能称逻辑预算等于真实物理内存上限。

RAM-hit 应是已经在后端可用的状态；若实际路径是从 RAM 中的序列化字节导入，单列 RAM-state-restore，计入导入成本，不称为零恢复开销直接复用。多上下文或多序列复用也要计量额外上下文及池开销。

OS 文件页缓存独立于应用历史预算。限制应用缓存并不能保证恢复来自 SSD，需单独描述系统缓存状态。

### 6.2 容量估算

Qwen3-1.7B 按 28 层、8 个 KV 头、头维度 128、FP16 估算，每 token 原始 KV 约 112 KiB，4096 token 约 448 MiB。实际状态序列化可能带有元数据、token 记录、布局与对齐开销，实验使用测量字节数，不以理论值代替日志。

状态、原始日志和图表初步预留 20—40 GiB，按实际对象数修订。模型、数据、状态三类存储分别记录；设置缓存文件总量上限和实验结束后的保留清单。容量压力通过限制实验预算产生，不通过耗尽整机 RAM 制造系统交换。

### 6.3 缓存键和对象状态

缓存键至少关联模型哈希、tokenizer/模板版本、完整前缀 token、位置配置、K/V 精度与布局、状态格式和后端版本。哈希用于检索，必要的长度与配置仍校验。

对象状态至少区分不存在、待写、写入中、磁盘就绪、读取中、后端就绪、失效。文件存在与可正确恢复不是同一状态。临时文件写完并校验后发布，读取失败回退重算；未完成写入不能发布命中。当前计算、读取与写入仍引用的对象不能提前释放或覆盖。

第一版完整对象导入，不能从不透明文件任意切出半段 KV。部分匹配仅使用独立保存且兼容的较短前缀对象。取消等待意味着请求改走重算，不保证已提交 I/O 被设备撤销；迟到结果要靠任务标识隔离，并计入废弃 I/O。

## 7 基线和比较公平性

### 7.1 恢复与选择策略

| 标识 | 方法 | 语义 |
|---|---|---|
| B0 | 无跨请求复用 | 每次计算完整输入；当前请求 Decode KV 正常存在 |
| B1 | 仅 RAM 复用 | 在统一预算内保留历史状态，淘汰后重新计算 |
| B2 | RAM＋SSD 完整恢复 | RAM 未命中、SSD 有兼容对象时恢复完成再继续 |
| B3 | RAM＋SSD 固定超时 | 等待完成或超时，未完成则重算 |
| B4 | RAM＋SSD 不额外等待 | 仅使用已经就绪的状态，无就绪对象则重算 |
| P1 | 轻量成本选择 | 估计未来恢复与重算耗时，收益超过裕量才选恢复 |

B3/B4 借鉴 HiCache 等待语义，不声称是原版策略实测。B4 的提前窗口必须来自同样的请求到达信息、队列或明确工作，不可使用未来问题；无窗口时退化为重算如实记录。没有安全部分发布能力时，所有组以完整对象为粒度。

初版统一 LRU 淘汰、同样缓存预算、同样保存对象规则和写出方式。查找、验证和管理开销计入各策略；B0 不人为增加无需执行的缓存开销。首先 B0/B1/B2 打通，再根据收益进入 B3/B4/P1。

固定超时先由校准耗时分位数提出候选档位，选出校准集上表现较好且资源代价可接受的设置后冻结。成本策略获得的调参数据和机会应与固定策略可比。结果同时报告所有预注册基线及选定固定基线，不能事后为每个测试请求选最快基线再当作可执行方法。

### 7.2 后台写入对照

| 标识 | 方法 | 定义 |
|---|---|---|
| W0 | 不保存 SSD | 不创建新增磁盘历史状态 |
| W1 | 同步保存 | 在规定请求阶段同步执行保存 |
| W2 | 普通异步保存 | 及时提交，但仍有统一安全内存上限 |
| W3 | 受限异步保存 | 限制写并发与在途字节，需求读取时推迟新可选写 |

同步保存统一定位为“生成完成后、返回完成确认前保存”，让其影响端到端完成时间；若更改阶段则另列配置，不用只看 TTFT 掩盖同步成本。异步组统一写完成语义。初版可选“文件数据提交并关闭后逻辑可用，但不保证断电持久化”；后台 flush 可能继续，报告系统 I/O 和静默收尾时间。若增加强制持久化组，单独比较，不与普通组混用。

写并发初步候选为 1、2、4，在途预算依据真实对象大小设置，至少容纳一份最大目标对象或明确规定超大对象跳过规则。W2 不是无限内存队列，W3 也不能以额外内存换取优势。对象筛选规则保持一致，初版不加入复杂复用预测。

## 8 实验阶段与验收

### E0 环境冻结和可观测性

目标是得到可信的运行环境、配置文件和事件日志。材料为硬件清单、CPU 后端、模型、固定提示、计时与系统监控工具。

完成 CPU 路径确认、模型预热、线程校准、计时精度检查、请求 ID 与状态 ID 贯通。确认后端内部自动前缀缓存、会话记忆及服务端隐藏缓存是否禁用或受控，避免 B0 意外复用。以空操作与固定短输入估计日志、接口或 HTTP 开销；优先同一进程关键路径，若用服务接口，则所有组相同并报告客户端与服务端时间。

验收：能重建同一配置，稳定重复推理，知道每个计时段代表什么，能辨别实际处理的前缀 token 数。交付 environment、模型 manifest、参数配置和样例日志。

### E1 状态正确性

目标是证明保存—恢复—继续推理有效。先 0.6B 的约 1024-token 前缀，再在主模型验证。

覆盖完整命中、兼容短前缀命中、不命中、配置不兼容、损坏或不完整对象、内存不足与恢复失败。验证恢复 token 数、位置、实际 Prefill 数、同一问题首步 logits 及固定后续 token 的多步 logits。

记录最大绝对误差、均值/均方误差、top-1 一致性；先测重复重算波动并冻结容限。贪心输出分歧要解释近并列 logits 或状态错误，不仅用文本相似判断。源状态生命周期和迟到读取也纳入检查。

验收：两模型目标配置恢复正确，异常可拒绝或回退。交付正确性矩阵、误差记录、失败案例和原型版本。未通过不进入性能结论。

### E2 单请求读算边界

目标是测前缀计算、不同恢复路径和完整请求 TTFT。固定主模型、单请求、无后台保存竞争、代表问题后缀和输出配置。

前缀长度为 256/1024/2048/4096 token。路径为完整重算、后端 RAM 就绪复用、热文件恢复、经确认的冷 SSD 恢复；RAM 序列化导入若存在另列。每路径先预热，再独立重复至少 30 次，状态设置和测试顺序随机化或平衡化。

分解查找、读取、验证/复制、导入、剩余 Prefill、首次生成；单次总时间以请求时间线为准。只读文件的微基准可辅助解释，不代替完整状态恢复。缓存准备时间单独记录，并在后续回放中计入新增保存成本。

验收：正确恢复与真实缓存态证据齐全，给出正收益、负收益和不确定区间。若冷态无法确认，只交付热态与未知态结果，不宣称冷 SSD 边界。交付读算表、耗时分解和边界图。

### E3 历史容量和请求复用

目标是检验 SSD 对容量不足的历史复用是否有价值。使用多文档轨迹，先比较 B0/B1/B2。

扫描历史预算 256/512/1024 MiB，工作集约为预算的 0.5 倍和 2 倍，重复机会 0/50/100%。先固定其余参数逐项扫描，再选择代表组合；不强求每个长度的 20 份文档都能实现全部工作集目标。

为 0% 轨迹提供足够不同前缀，或标明窗口内重复机会定义；100% 轨迹需先经历首次构建，不能把首次请求凭空当作已有缓存。分别报告预置缓存条件结果与从空缓存开始的完整结果，后者包含生成、保存、淘汰及恢复。

验收：预算与真实内存计量可信，状态转移能解释实际命中，重建初始状态后结果可重复。交付预算—延迟—命中对照与工作集记录。

### E4 固定策略和成本选择

进入条件：E2/E3 表明有收益或选择错误成本，值得增加决策。

P1 使用已观测前缀长度、状态字节、读取/导入时间和 Prefill 速度，估计从当前时刻恢复与重算的剩余 TTFT。若重算估计减去恢复估计大于误差裕量，则选择恢复；否则重算。已等待时间计入最终 TTFT，但不重复当作未来恢复成本。

先采用能解释的查表或分段拟合，不预设复杂学习模型。把在线预测、查找、线程调度及额外缓冲开销计入时间与内存。固定超时、误差裕量及更新方式在校准集上确定。

正式比较 B2/B3/B4/P1，先空闲 I/O，必要时添加受控写入档位。压力档位按测得 SSD 与对象恢复性能校准，不能为制造结果而只选择极端负载。并发 2 仅代表配置，并保持同样到达信息。

验收：与公平调参基线比较，有独立测试轨迹和预测误差记录。交付策略结果、选择次数、超时、废弃 I/O、预测偏差与开销。如 P1 无稳定增益，保留固定方法并说明原因。

### E5 后台写入干扰

固定读取策略、对象筛选和淘汰规则，分成两个实验。

实验 A 使用相同预置读取对象和固定写任务，隔离 CPU、RAM 与 SSD 竞争；比较 W0/W1/W2/W3。实验 B 从相同初始缓存回放完整轨迹，允许写入差异影响未来可用状态，观察延迟收益是否被命中损失或重算抵消。

记录首 token、端到端完成、生成 token 间隔、写出吞吐、应用队列和 OS I/O、源缓冲占用、任务丢弃和收尾时间。W0 在实验 A 可读取同样预置状态，但不新增保存；实验 B 没有新增 SSD 状态，结果解释其差异。

验收：写完成口径一致、没有提前释放源对象、没有把后台积压排除计时。交付干扰曲线、命中与积压权衡，以及适用条件。

### E6 消融、稳健性和复测

针对最终关键配置执行，而不是重新穷举所有组合。可包括：P1 去掉误差裕量；固定估计与在线更新；W3 仅限制并发、仅限制在途字节、增加读取优先；中文与英文分别统计；0.6B 与 1.7B 代表比较；不同日期/温度条件独立复测。

若最终方案同时使用 P1 与 W3，用“固定读取＋普通写、P1＋普通写、固定读取＋受限写、P1＋受限写”四组辨别来源。仅加入实验已表明有意义的组件，不把无收益模块包装成贡献。

验收：主要结论在独立轮次成立，收益及代价来源可解释。交付消融表、不利场景、适用范围与复现说明。

## 9 请求到达、计时和监控口径

### 9.1 到达方式

第一轮使用串行闭环回放：上一请求完成后提交下一请求，用于比较服务路径，无外部到达队列。此时 P95 反映服务与缓存变化，不宣称代表生产排队。

后续用冻结到达时间的开环轨迹检验排队与并发。到达率由校准吞吐确定，先选择能稳定服务的范围；所有策略收到相同时间表。如果到达率超过处理能力，报告队列增长、截止时未完成请求及排空时间，不删除慢请求，也不把不稳定系统的 P95 当作长期稳态结果。

### 9.2 指标定义

| 指标 | 统一口径 |
|---|---|
| TTFT | 首个生成 token 就绪时间减请求到达时间，含排队、查找、恢复和剩余计算 |
| 用户可见首文本时间 | 首个可见文本片段时间，和首生成 token 分开，避免空白/特殊 token 差异 |
| 端到端延迟 | 完成确认减到达时间，包含预定同步保存阶段 |
| 服务时间 | 实际开始处理到完成，不与排队重复计量 |
| 生成间隔 | 相邻生成 token 时间差，保留分布 |
| 吞吐 | 测量窗口请求数/时间及输出 token 数/时间，说明窗口和收尾是否包含 |
| 真正复用量 | 后端实际少计算的有效连续前缀 token |
| 资源 | 进程驻留/提交内存、KV 池、历史对象、缓冲、读写量和队列 |
| 后台代价 | 写任务积压、放弃对象、无效读取、前台结束后的排空时间 |
| 决策可靠性 | 预测误差、选择比例、超时比例、决策本身耗时 |

使用同一单调时钟记录相关事件。单线程日志写盘可能竞争同一 SSD，优先缓冲日志、统一采样频率并量化监控开销；详细系统跟踪单列验证轮次，不能只给某个策略增加跟踪负担。

### 9.3 请求级日志字段

至少包括 run_id、配置哈希、模型哈希、数据划分、种子、请求 ID、文档/状态 ID、计划到达时间、真实到达时间、开始处理时间、输入/共同前缀/实际复用 token 数、状态字节、预算、缓存态、选择动作、预测值、各阶段事件、首 token、完成时间、输出 token 数、内存、错误与回退。

轮次级日志保存温度、频率、CPU/SSD 活动、异常后台任务、预热条件、策略顺序和初始缓存清单。缺测字段标明缺测，不能用理论估计冒充硬件测量。

## 10 冷热文件缓存与 SSD 证据

状态文件在 SSD 上不代表恢复来自物理 SSD。热态文件可能主要命中 OS RAM，重启进程不会自动清除文件页缓存。应用逻辑缓存淘汰与 OS 缓存驱逐分别处理。

| 状态 | 判定依据 | 可以做的表述 |
|---|---|---|
| 后端就绪 RAM | 活动或可挂接状态已存在，无文件读取 | RAM 复用 |
| RAM 序列化状态 | 从内存缓冲导入 | RAM 状态恢复 |
| 文件热态 | 明确预读，确认低实际磁盘读取 | 热文件恢复 |
| 文件冷态 | 缓存控制流程＋目标读取关联的系统 I/O 证据 | 经验证的冷 SSD 恢复 |
| 未知态 | 无法确认是否有 OS 缓存 | 文件缓存状态未知 |

准备 Windows 原生系统跟踪/性能监控工具，记录文件读取与磁盘读活动。仅进程逻辑读取字节和 Resource Monitor 截图不一定足以证明单个目标读取来自磁盘，应结合目标路径、时间窗与系统 I/O 归因。排除模型缺页、后台下载等无关读取。

具体冷态控制方法在 E0/E2 另行验证。若采用绕过缓存或自定义 I/O，需要考虑对齐、接口与计时变化，作为独立方法说明，并保持各恢复策略一致；不能把它和普通文件读取结果无说明合并。全局驱逐可能同时影响模型权重，应监控权重读取并建立恢复测量与模型常驻可同时成立的流程。

无法验证冷态时，先完成热态和真实日常缓存态实验，保留研究价值，同时明确冷 SSD 结论尚缺证据。

## 11 实验矩阵、样本与统计

### 11.1 分层矩阵

| 轮次 | 因素 | 规模控制 |
|---|---|---|
| 接口验证 | 两模型、关键恢复/失败情形 | 少量样例，优先正确性 |
| 微基准 | 主模型、4 个长度、3—5 条可证实路径 | 每配置至少 30 次 |
| 容量筛选 | 预算、工作集比例、重复机会 | 一次改变一项，短轨迹筛选 |
| 正式策略 | 代表空闲/竞争条件、固定与成本方法 | 至少 3 种子，每种子至少 100 请求 |
| 写入与消融 | 代表读取/生成负载、4 写法与有效组件 | 对关键配置独立复测 |

这些是起步下限，不保证充分统计功效。按样本波动和结论所需精度增加轮次；先估计运行成本，避免把全部参数笛卡尔积直接作为首轮任务。

### 11.2 配对与不确定性

同文档、请求轨迹与种子做配对比较；策略顺序随机化或平衡化。请求共享缓存历史，不能把相邻请求当作完全独立样本。首轮报告各轮次中位数/P95、轮次范围和配对差值；只有 3 轮时明确不确定性较大。需要稳定置信区间时增加独立轮次，再按轮次或合理时间块进行 bootstrap，方法与次数公开。

延迟收益定义为基线延迟减候选延迟；相对下降为该差值除以基线延迟。P95 的相对改善与每请求平均改善不同，分别说明。不同语言、长度、缓存态及负载分层报告，不能仅给混合平均数。

不因某次很慢就删除；只有预先定义的系统异常才能标记无效，保留原始记录、理由和补测。样本不足不宣称 P99 改善。超时、失败和未完成请求始终报告。

### 11.3 结果判断

正确性通过、收益超过重复测量波动、关键资源代价可接受，才支持优化有效。可把“主指标至少约 5% 改善且没有明显内存、尾延迟或积压恶化”作为初步工程关注线，校准后与老师确定；该百分比不是理论标准，也不替代统计证据。负结果仍按设备、模型、范围报告。

## 13 进度与阶段决策

按每周约 12—18 小时投入估算六周，实际以验收为准，不把安排写成已完成结果。

| 时间 | 主要任务 | 必须交付 | 决策 |
|---|---|---|---|
| 第 1 周 | E0/E1 环境、日志和恢复 | 环境表、正确性报告、最小原型 | 恢复失败优先修接口 |
| 第 2 周 | E2 读算与缓存态 | 边界表、实际字节及分解图 | 冷态不可证实时限制表述 |
| 第 3 周 | E3 容量和基线 | B0/B1/B2 回放、预算记录 | 无收益则转向 RAM/写出筛选 |
| 第 4 周 | 条件满足后 E4 | 固定策略与 P1 独立测试 | 固定足够则不增加复杂度 |
| 第 5 周 | E5 写入竞争 | 干扰与命中/积压权衡 | 无竞争则记录不适用范围 |
| 第 6 周 | E6 与整理 | 复测、消融、日志、结论 | 决定扩展或继续聚焦 |

每周汇报四项：本周已验证什么、证据在哪里、尚未解决什么、下一周的验收条件。若接口工作超过一周，先完成一个模型和较短前缀，减少参数与后续并发范围，不能跳过正确性。

## 14 失败情形与替代路线

| 情形 | 首先检查 | 可调整方向 |
|---|---|---|
| 恢复后 logits 不一致 | token、位置、格式、精度、上下文能力 | 修正接口或换兼容后端 |
| B0 意外很快 | 隐藏自动缓存、状态未清空、Prefill token 数 | 修正基线隔离 |
| RAM 预算似乎无效 | 预分配池、隐藏引用、序列化副本 | 分离逻辑预算与物理计量 |
| SSD 始终优于重算 | 是否其实文件热态，计算是否配置不佳 | 确认缓存态并考虑简单恢复规则 |
| SSD 始终慢于重算 | 恢复、导入成本与实际存储态 | RAM 复用、减少无效保存 |
| 自适应没有优势 | 是否真的存在路径切换、预测误差、最佳固定基线 | 保留固定规则，报告边界 |
| 异步写没有干扰 | 压力是否充分且合理、工作是否已完成 | 不人为夸大，限定适用范围 |
| 受限写当下快但后续慢 | 未保存造成命中损失、积压 | 报告完整轨迹权衡，调整保存规则 |
| 测量波动大 | 温度、功耗、后台 I/O、日志开销 | 重建环境并补独立轮次 |

跨设备、稀疏加载或 KV 量化若被选为新方向，应另立质量与兼容性问题，不能悄然替换本计划的精确复用目标。

8. 消融与稳健性：关键组件来源、不同模型/文本/独立轮次。
9. 明确结论：适用条件、负结果、未知缓存态和下一阶段。

图表优先使用中位数/区间曲线、延迟分解、预算曲线、策略配对差值与写入权衡图。没有证实的冷态、功率或稳定 P99 不放入已验证结论。

## 16 执行前需要确定的事项

已确定：个人设备、CPU-only、单 SSD、llama.cpp 路线、0.6B 调试与 1.7B 主实验、FP16 KV、完整前缀精确复用、先正确性再性能。

E0/E1 需要落实：后端提交、具体模型文件、实现方式、CPU 构建、token 模板和 logits 容限。

E2 前需要落实：线程与 batch 配置、计时事件、RAM 路径类型、冷热文件缓存证据与监控工具。

E3/E4 前需要落实：真实状态大小、预算计量、文档划分、轨迹到达、超时/估计器校准与测试冻结。

E5 前需要落实：写完成口径、任务提交时点、源对象引用、安全上限、受限写参数和收尾范围。

与老师重点讨论：CPU-only 主场景是否合适；先以读算边界作为阶段成果是否满足预期；单设备策略通过后再开展跨设备是否合适。其余常规实现选择可随阶段验证确定，不需要在开始前把所有细节一次定死。
