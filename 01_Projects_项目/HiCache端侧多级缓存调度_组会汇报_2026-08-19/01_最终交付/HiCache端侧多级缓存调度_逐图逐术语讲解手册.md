# HiCache 端侧多级缓存调度：逐图逐术语讲解手册

这份手册对应 10 页研究方向汇报 PPT。它的用途不是让你逐字背诵，而是帮助你理解每一页为什么存在、每张图表达什么、老师追问术语时应该怎样回答。

---

# 第一部分：整套 PPT 的逻辑链

整套 PPT 讲的是下面这条因果链：

```text
多轮对话、Agent、RAG 反复出现相同长前缀
                    ↓
这些前缀对应的 KV Cache 有复用价值
                    ↓
但端侧高速内存放不下不断增长的 KV Cache
                    ↓
冷 KV 被逐出后只能重新 Prefill，增加 TTFT 和能耗
                    ↓
借鉴 HiCache，把 KV 放入 L1、L2、L3 多个层级
                    ↓
端侧的数据搬运会与前台推理争抢统一内存带宽
                    ↓
不能只追求命中率，必须比较“加载”和“重算”的真实成本
                    ↓
提出 EAHS：以 value、deadline 和 phase 联合调度预取与写回
                    ↓
通过真实设备实验验证收益边界，允许得到否定结论
```

一句话总结研究方向：

> 研究如何在端侧有限内存和共享带宽条件下，只加载、保留和写回那些确实比重新计算更划算的 KV Cache。

## 第 2 页：KV 容量为什么成为端侧瓶颈

### 上方四个方框

四个方框是一条因果链：

```text
多轮会话、Agent、RAG 共享长前缀
        ↓
加速器中的 KV 池容量有限，旧前缀被逐出
        ↓
相同前缀再次到来时重新执行 Prefill
        ↓
TTFT、能耗和温升同时增加
```

它想说明：工作负载明明存在复用机会，但容量不足使机会丢失。

### 左下角容量公式

公式使用普通文字解释如下：

```text
KV Cache 总容量
= 2 × 模型层数 × KV 头数 × 每个头的维度
  × token 数量 × 每个数值的字节数
```

最前面的 2 表示同时保存 Key 和 Value。

以常见 Llama 3 8B GQA、FP16 KV 为量级示例：

```text
每个 token 的 KV 大小
= 2 × 32 层 × 8 个 KV 头 × 128 维 × 2 字节
= 131072 字节
= 128 KiB/token
```

这只是量级示例，不代表所有模型都固定为 128 KiB/token。

### 右侧三根横条

横条表示容量，不表示推理速度：

```text
8K token   ≈ 1 GiB
32K token  ≈ 4 GiB
128K token ≈ 16 GiB
```

横条长度随上下文长度线性增长。它想强调，即使模型采用 GQA，长上下文 KV 仍然可能占用数 GiB 到十几 GiB。

### 为什么 128K 的 16 GiB 很严重

因为 16 GiB 只是单条序列的 KV 量级，没有包含：

- 模型权重；
- 运行时和算子工作区；
- 激活值；
- 内存碎片和分页元数据；
- 操作系统及其他应用；
- 多请求并发。

因此端侧设备不能把全部历史 KV 长期保存在高速层。

### 本页应该得出的结论

> 长上下文首先造成容量压力；多级缓存的意义是让被逐出的 KV 仍有机会以低成本恢复。

## 第 3 页：服务器 HiCache 与端侧现实的对照图

### 左右两栏分别是什么

左栏是服务器侧 HiCache 已经具备的机制，右栏是端侧移植时新增的约束。

这不是两个互相竞争的系统，而是“原机制”和“迁移后问题”的对照。

### 左栏四行

#### 层次

```text
L1：GPU/HBM
L2：Host DRAM
L3：外部或分布式存储
```

服务器的不同层通常拥有比较明确的设备边界和带宽层次。

#### 预取

HiCache 可以在模型真正需要 KV 之前把数据从低层搬到高层，并选择是否等待。

#### 写入

模型生成的新 KV 可以立即写到低层、选择性写入，或者延迟到适当时机写回。

#### 并行

使用线程、队列和设备流，让数据搬运与模型计算重叠。

### 右栏四行

#### 内存

端侧 CPU、GPU、NPU 经常共享 LPDDR。L1 和 L2 可能不是两块完全独立的物理内存，而是不同的可见性、地址空间、布局或精度状态。

#### 竞争

Decode 需要不断读取 KV，本身已经依赖内存带宽；后台复制、格式转换或 UFS I/O 会抢占同一总线。

#### 成本

端侧需要考虑 UFS 尾延迟、能耗、温升、降频和闪存写入量。

#### 目标

不能只最大化命中率，还要同时约束 TTFT、ITL、能耗、温度和写入预算。

### 底部蓝色结论条

它明确指出研究切口：

> 把服务器上的固定阈值和固定写策略，改成由端侧在线成本模型驱动的读写联合调度。

## 第 5 页：Edge-HiCache 三级缓存架构图

### 这张图的性质

这是一张概念架构图，用于说明系统组成和数据流，不是实验结果，也不是某个真实芯片的内部结构图。

### 右侧 L1、L2、L3

#### L1：加速器可见 KV 池

模型当前可以直接访问和消费的 KV。速度最快、容量最小，是 Decode 真正需要的数据所在层。

#### L2：LPDDR 温缓存

KV 仍在设备内存中，但可能不处于加速器能够直接消费的格式或区域。使用前可能需要映射、复制、反量化或布局转换。

#### L3：UFS/SSD 持久前缀

保存未来可能再次复用的长前缀。容量最大，但读取延迟、尾延迟、能耗和写入代价最高。

### 为什么 L1/L2 都可能在 LPDDR 中

在统一内存设备上，层次不一定完全由物理介质决定，也可以由以下条件决定：

- 加速器是否能直接访问；
- 数据是否已经映射；
- KV 的精度是否匹配；
- 张量布局是否匹配；
- 是否需要复制到连续 page。

因此端侧层次更准确的说法是“可消费状态层次”，而不仅是物理存储层次。

### 左侧白色区域

左侧表示控制面和元数据，不是另一块缓存。

#### EdgeRadix

按 token 前缀组织缓存索引。它记录：

- token 前缀；
- page 位于 L1、L2 还是 L3；
- 热度和最近访问时间；
- 模型版本和 tokenizer；
- 位置编码配置；
- KV 精度、形状和布局版本。

#### 控制动作

- prefetch：提前读取；
- cancel：取消已经不再划算的任务；
- write：写入低层；
- evict：逐出低价值 KV；
- recompute：放弃等待，重新 Prefill。

### 图中的上下箭头

向上表示加载或提升，向下表示备份、降级或写回。箭头不代表每个 page 必须依次经过全部层级。

### 底部接口说明

为了降低实现难度，第一版运行时只要求提供：

```text
prefix_match：查询可复用前缀
page_load/store：读取或写入 KV page
phase：当前处于 Prefill、Decode 或空闲阶段
观测接口：时间、带宽、能耗和温度
```

## 第 6 页：EAHS 收益函数和调度器图

### EAHS 是什么

EAHS 是 Edge-Adaptive Hierarchical Scheduler 的缩写，是本研究暂定的端侧自适应分层缓存调度器名称。

它的核心原则是：

```text
只有“预计避免的重算代价”大于“数据移动及其副作用”时，才执行缓存操作。
```

### 读收益公式怎样理解

不要死记数学符号，可以记成：

```text
读收益
= 复用概率 × 避免的重算时间
  − KV 加载完成时间
  − 能耗惩罚
  − 对前台推理的干扰惩罚
```

各项含义：

- p_i：第 i 个 page 被真正复用的概率；
- C_i：不加载时重新计算它需要的时间；
- R_i：从当前层加载到可消费层需要的完成时间；
- E_i：本次搬运的能耗；
- I_i：本次搬运对 TTFT 或 ITL 的干扰；
- lambda：把不同代价转换成统一权重的系数。

当读收益大于 0，并且可以在 deadline 之前完成时才执行。

### 为什么是加载“完成时间”而不只是传输时间

因为实际数据路径可能包括：

```text
排队 + UFS 读取 + 内存复制 + 反量化/格式转换 + 同步等待
```

只测理论带宽会低估真实成本。

### 写收益公式怎样理解

```text
写收益
= 未来复用可能节省的计算与加载成本
  − 当前写入时间
  − 闪存写入机会成本
  − 占用持久层容量的机会成本
```

它用于决定新 KV 是否值得长期保存。

### 右侧调度器图

#### 左侧输入

- deadline：数据必须到达的最晚时间；
- 复用概率：page 未来或当前被使用的可能性；
- 实时带宽：当前可用于搬运的带宽；
- phase：当前运行阶段；
- 能耗状态：电量、功耗或热状态。

#### 中间控制器

根据在线成本模型计算 value，决定接收、取消、抢占或降级任务。

#### 读队列

优先处理高价值且即将到期的加载任务。

#### 写队列

只接收未来价值为正的 page；当前台 Decode 受影响时可以暂停或抢占。

#### 底部“保护前台 Decode”

这是端侧算法与普通后台缓存任务的重要区别。交互式生成的流畅度比尽快完成后台写更重要。

## 第 7 页：技术路线和 phase 门控图

### 上方 A 到 E 五个阶段

#### A：Microbenchmark

单独测量重算时间、数据加载时间、能耗和前台干扰，得到基础成本曲线。

#### B：在线成本模型

运行时持续更新带宽、尾延迟、温度和 slowdown，使调度适应设备动态变化。

#### C：静态基线

复现固定预取和固定写策略。没有可靠基线，就无法判断 EAHS 是否真正有效。

#### D：EAHS 原型

加入双队列、value、deadline、取消和抢占。

#### E：真实端侧评估

在真实设备和真实 workload 上测量 TTFT、ITL、能耗、温度和写入量。

### 下方 phase 门控时间带

#### Decode

逐 token 生成，对延迟波动敏感。应该保护内存带宽并抢占低优先级写。

#### Prefill

一次性处理输入，计算密度通常高于 Decode。只有在 slowdown 可控时才允许后台任务重叠。

#### Queue Slack

前台请求队列存在空隙，但系统不一定完全空闲。此时优先完成即将到 deadline 的读。

#### Idle

系统真正空闲时合并并排空高价值写任务。

### 底部回流箭头

表示预测值与真实测量值之间的误差会反馈给成本模型。例如预测加载需要 20 毫秒，实际用了 45 毫秒，后续任务的 R 值应被提高。

### 红色止损条件

如果大量场景满足：

```text
加载时间 R ≥ 重算时间 C
```

说明多级读取缺乏收益。此时应当转向 KV 量化、选择性重算或加载—重算联合选择，而不是继续堆叠调度规则。

# 第三部分：术语词典

## A. 大模型推理基础

| 术语 | 含义 | 在本课题中的作用 |
|---|---|---|
| LLM | Large Language Model，大语言模型 | 研究对象 |
| Transformer | 以注意力机制为核心的模型结构 | KV Cache 产生于其注意力层 |
| Attention | 根据 Query、Key、Value 计算 token 之间的相关性 | Decode 需要读取历史 K、V |
| Query / Key / Value | 注意力中的查询、键和值 | KV Cache 保存历史 Key 和 Value |
| token | 模型处理文本的基本离散单位，不一定等于一个汉字或单词 | 上下文和 KV 容量的计量单位 |
| context | 当前请求能够看到的输入与历史 token | 越长意味着 KV 越多 |
| prefix | 请求开头连续相同的一段 token | 可以跨请求复用其 KV |
| long context | 长上下文，通常指几千到十几万 token | 造成端侧 KV 容量压力 |
| Agent | 会调用工具、规划和多轮交互的大模型应用 | 经常重复系统提示和历史上下文 |
| RAG | Retrieval-Augmented Generation，检索增强生成 | 请求中经常含固定模板和重复检索前缀 |
| Prefill | 一次性处理输入 token，并生成对应 KV | 长输入下计算成本高，可被缓存复用减少 |
| Decode | 基于已有 KV 逐 token 生成输出 | 对内存带宽和延迟波动敏感 |
| recompute | 不读取缓存，重新计算对应前缀 | 当加载不划算时的退路 |
| repeated Prefill | 相同前缀因缓存不可用而被再次计算 | 本研究希望减少的浪费 |

## B. KV Cache 与容量

| 术语 | 含义 | 注意点 |
|---|---|---|
| KV Cache | 保存历史 token 在各层产生的 Key 和 Value | 提速但占用大量内存 |
| KV head | 生成 Key、Value 的注意力头 | 头数越多，KV 越大 |
| head dimension | 每个注意力头的维度 | 与 KV 容量成正比 |
| GQA | Grouped-Query Attention，多组 Query 共享较少的 KV 头 | 降低 KV 容量，但不能消除长上下文增长 |
| MHA | Multi-Head Attention，每个 Query 头通常有对应 KV 头 | KV 通常比 GQA 更大 |
| MLA | Multi-head Latent Attention，通过低维潜变量压缩 KV 表示 | 会改变容量公式和存储格式 |
| FP16 | 16 位浮点数，每个数值通常占 2 字节 | PPT 容量示例的精度 |
| KV quantization | 把 KV 从 FP16 压到 INT8、INT4 等更低位宽 | 省容量和带宽，但可能影响精度并产生转换开销 |
| KiB | 1024 字节 | 128 KiB 等于 131072 字节 |
| GiB | 1024 的三次方字节 | 与十进制 GB 略有区别 |
| page | 一组连续 token 对应的 KV 管理块 | 搬运、逐出和调度的基本单位 |
| page fragmentation | page 未完全利用或分配不连续造成的浪费 | 实际占用可能高于理论值 |

## C. 性能指标

| 术语 | 含义 | 好坏方向 |
|---|---|---|
| TTFT | Time To First Token，从请求到达至首 token 输出的时间 | 越低越好 |
| ITL | Inter-Token Latency，相邻输出 token 之间的延迟 | 越低、越稳定越好 |
| throughput | 单位时间完成的 token 或请求数量 | 通常越高越好 |
| p50 | 一半样本不超过该值，中位数 | 表示典型体验 |
| p95 | 95% 样本不超过该值 | 表示尾部体验，比平均值更能暴露卡顿 |
| tail latency | 尾延迟，较慢请求或 I/O 的高分位延迟 | UFS 和共享资源竞争时尤其重要 |
| slowdown | 加入后台任务后，前台耗时相对基线增加的比例 | 越低越好 |
| memory-bound | 性能主要受内存带宽限制，而非算力限制 | Decode 常见状态 |
| break-even | 两种方案成本相等的临界点 | 用于判断加载从何时开始优于重算 |

## D. 缓存层次与硬件

| 术语 | 含义 | 在本课题中的位置 |
|---|---|---|
| L1/L2/L3 | 从快到慢、从小到大的缓存层级 | 分别对应可消费 KV、温缓存和持久层 |
| HBM | High Bandwidth Memory，高带宽显存 | 服务器 GPU 常用的 L1 |
| Host DRAM | CPU 主内存 | 服务器 HiCache 常用的 L2 |
| LPDDR | 移动设备低功耗内存 | 端侧 CPU/GPU/NPU 常共享 |
| unified memory | 处理器共享一套物理内存或统一地址空间 | 导致前后台任务争抢同一带宽 |
| UFS | 手机常用闪存存储接口 | 端侧候选 L3，容量大但延迟和写入代价高 |
| SSD | 固态硬盘 | Jetson 或边缘设备的候选 L3 |
| NPU | Neural Processing Unit，神经网络加速器 | 端侧模型主要执行设备之一 |
| GPU | 图形处理器，也可用于大模型推理 | 原型平台和候选 L1 |
| Jetson | NVIDIA 边缘计算平台 | 便于控制 CUDA、内存和测量的原型平台 |
| CUDA | NVIDIA GPU 编程和运行时平台 | 可用于实现与测量原型 |
| Ascend | 华为昇腾 AI 计算平台 | 可能的目标平台，需确认 KV 接口 |
| MindIE | 面向昇腾的推理引擎 | 可能的系统接入层 |
| thermal throttling | 设备过热后降低频率 | 可能使长时间实验性能恶化 |
| flash wear | 闪存写入带来的寿命消耗 | 写回收益函数中的成本之一 |

## E. HiCache 与缓存策略

| 术语 | 含义 | 作用 |
|---|---|---|
| HiCache | SGLang 的分层 KV 缓存机制 | 本课题的机制来源和服务器基线 |
| SGLang | 面向大模型推理的开源系统 | HiCache 所在框架 |
| RadixAttention | 使用 Radix Tree 组织共享前缀及 KV | 支持连续前缀匹配和复用 |
| prefix_match | 查询当前请求与已有缓存的最长连续前缀 | 决定可复用范围 |
| cache hit | 需要的数据存在于某一级缓存 | 还必须考虑能否及时到达 |
| cache miss | 所有可用层都没有所需数据 | 通常需要重新计算 |
| prefetch | 在真正需要之前提前加载数据 | 用于隐藏加载延迟 |
| demand load | 当前请求已经确定需要时才加载 | 复用概率通常可视为 1 |
| best_effort | 尽力使用缓存；未及时到达时放弃等待 | 避免无限阻塞 |
| wait_complete | 等待缓存加载完成再继续 | 命中收益高但可能增加尾延迟 |
| timeout | 最多等待一段时间，超时后重算或降级 | 静态折中策略 |
| write-through | 新 KV 生成后立即写入低层 | 简单可靠，但写放大和干扰较大 |
| selective write | 只写未来价值较高的 KV | 减少无效写入 |
| write-back | 先保留在高层，合适时再批量写入低层 | 可合并写，但需要一致性管理 |
| evict | 为释放容量而逐出缓存数据 | 应优先逐出低价值 page |
| offload | 把数据从加速器内存转移到 CPU 内存或存储 | 降低高速内存占用 |
| backup queue | 将 KV 备份到低层的任务队列 | HiCache 写路径的一部分 |
| device stream | 设备上的异步执行流 | 用于重叠计算和搬运 |

# 第四部分：最容易被老师追问的区别

## 1. 缓存命中率高，为什么性能仍可能差

因为命中的数据可能位于很慢的 UFS，或者搬运时与 Decode 争抢带宽。真正有用的是“及时且低成本的命中”。

## 2. 预取与需求加载有什么区别

需求加载已经确定当前请求需要，复用概率接近 1；预取是在未来是否需要尚不确定时提前搬运，可能浪费资源。

## 3. 异步为什么不等于没有成本

异步只表示调用线程不原地等待。后台任务仍然消耗带宽、能量、队列、缓存容量，并可能影响前台延迟。

## 4. 端侧 L1/L2 为什么可能共享同一物理内存

因为统一内存设备中，CPU、GPU、NPU 可能共享 LPDDR。层级差异可能来自可见性、映射、精度和布局，而不是完全不同的物理介质。

## 5. 为什么第一版不同时做 KV 量化

同时引入量化会把精度误差、转换开销和调度收益混在一起。先用精确 KV 验证调度，再做量化消融，更容易解释结果。

## 6. EAHS 与普通 LRU 有什么区别

LRU 主要依据最近使用时间决定保留和逐出；EAHS 还考虑复用概率、重算成本、加载完成时间、deadline、能耗、前台干扰和运行 phase。

## 7. 为什么需要读写联合调度

读任务决定当前请求是否等待，写任务决定未来是否有缓存可用。两者共享带宽、能量和容量，分开优化可能导致后台写破坏当前 Decode。

## 8. 研究失败时能得到什么

可以得到端侧加载与重算的 break-even 边界，说明哪些模型、上下文、设备和 workload 不适合多级 KV。这仍然是可复现、可发表的系统结论。
