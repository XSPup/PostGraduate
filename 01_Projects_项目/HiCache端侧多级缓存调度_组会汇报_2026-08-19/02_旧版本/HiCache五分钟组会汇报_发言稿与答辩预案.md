## 二、逐页发言稿

### 第 1 页：标题

建议用时：15 秒。

老师好，我接下来汇报拟开展的研究方向：面向端侧大模型推理的分层 KV 缓存调度。我的目标不是把服务器版 SGLang 原样搬到端侧，而是提取 HiCache 的分层与异步调度机制，再针对统一内存、能耗和闪存约束重新设计调度算法。

转场：首先解释为什么端侧需要这项研究。

### 第 2 页：研究背景——问题与容量

建议用时：35 秒。

在多轮会话、Agent 和端侧 RAG 中，请求会反复共享系统提示、历史会话或文档前缀。但是加速器可用 KV 池有限，长前缀被逐出后，后续请求只能重新执行 Prefill。

KV 容量随层数、KV 头数和上下文长度线性增长。以常见 Llama 3 8B GQA、FP16 KV 为量级示例，每个 token 约占 128 KiB，32K 上下文约为 4 GiB。

所以问题不只是提高命中率，而是冷 KV 能否以比重算更低的代价恢复。

转场：服务器侧 HiCache 已经提供了一个可参考的答案。

---

### 第 3 页：研究背景——HiCache 与端侧差异

建议用时：30 秒。

HiCache 已经提供 GPU、Host DRAM 和外部存储三级 KV 缓存，也提供 best-effort、wait-complete、timeout 三类等待方式，以及 write-through、selective、write-back 三类写策略。

但端侧的 L1 和 L2 往往共享 LPDDR，Decode 本身又是 memory-bound。后台读取、写入和格式转换会直接抢占前台带宽，并带来 UFS 长尾、能耗、温升和闪存写入成本。

因此我把 HiCache 作为机制和静态基线，研究端侧在线成本驱动的读写联合调度。

转场：基于这个差异，我把研究内容拆成三个可以被实验否定的问题。

---

### 第 4 页：研究内容——三个问题与候选创新

建议用时：35 秒。

第一个问题是哪些 HiCache 机制可以迁移。我准备保留分页、Radix 前缀和异步状态机，并加入模型、tokenizer、位置编码和 KV 格式版本，形成 EdgeRadix。

第二个问题是一个 page 什么时候值得读。候选方法是 deadline 和 value 驱动的自适应预取。

第三个问题是新 KV 什么时候值得写。候选方法是 phase-aware 选择性写回，读写双队列可以被前台 Decode 抢占。

这里不声称首次做多级缓存。需要验证的是端侧持久前缀、统一内存干扰和读写联合调度的组合是否形成新贡献。

转场：这三个问题对应下面的系统结构。

---

### 第 5 页：研究内容——Edge-HiCache

建议用时：35 秒。

我拟议的 Edge-HiCache 包含三层数据面。L1 是加速器当前可以直接消费的 KV；L2 是 LPDDR 中需要映射、复制或格式转换的温缓存；L3 是 UFS 或 SSD 中的持久前缀。

EdgeRadix 保存 token 前缀、page 位置、热度和模型及格式版本。EAHS 控制器只通过最小接口执行预取、取消、写回、逐出和重算。

第一版先用精确 KV 验证调度收益，量化放到后续扩展和消融，避免同时改变两个变量。

转场：控制器怎样判断读还是重算、写还是不写，是算法核心。

---

### 第 6 页：技术路线——EAHS 收益模型

建议用时：45 秒。

EAHS 把预取和写回写成统一的收益判断。

读收益等于可能避免的重算时间，减去加载完成时间、能耗和对前台的干扰。需求加载时使用概率为一，预测性预取时使用概率小于一。只有收益为正，并且能在 deadline 前完成时才进入读队列。

写收益还要扣除写入时间、闪存写入机会成本和持久层容量成本。只有正收益 page 才进入写队列，相邻 page 会合并写。

读队列按 value 和最早截止时间调度，写队列可以被 Decode 抢占。收益转负、错过 deadline 或前台受扰时，预取会被取消并转为重算。

转场：有了收益模型以后，还要把它接到真实运行时中。

---

### 第 7 页：技术路线——实现与 phase 门控

建议用时：35 秒。

技术路线分五步。首先做 microbenchmark，测量重算时间、加载时间、前台干扰和能耗；然后建立在线成本模型；第三步复现 HiCache 静态策略；第四步实现 EAHS；最后在真实端侧评估。

运行时按 phase 门控：Decode 时保护总线并抢占写；Prefill 时只允许可控重叠；队列空隙优先完成即将到期的读；Idle 时合并并排空高价值写。

我还设置了止损条件：如果真实 workload 中加载普遍不如重算，就转向 KV 量化或加载—重算选择，而不是继续增加调度复杂度。

### 第 8 页：研究基础

建议用时：30 秒。

研究基础有四层。原理上，RadixAttention 已支持连续前缀匹配；代码上，HiCache Controller 已有异步读写队列、设备流和按层搬运；平台上，可以从 Jetson、Android 运行时或 Ascend/MindIE 的可用接口选择切入点；相关工作也已覆盖分层 KV、CPU/SSD offload、量化和加载—重算选择。

这些工作证明机制可行，但也意味着不能声称首次。真正需要证明的是端侧联合调度能否带来稳定的增量收益。

## 三、老师可能询问的问题与回答预案

### 1. 这不就是普通的多级缓存吗？创新在哪里？

回答：

多级缓存本身不是创新，HiCache、Mooncake 和 Host-SSD 工作都已经存在。本课题的候选贡献是端侧统一内存和本地持久闪存约束下，使用 deadline、value 和 phase 对读预取与选择性写回进行联合调度，并显式建模前台干扰、能耗和写入预算。最终创新性需要通过进一步检索和基线复现确认。

### 2. 为什么不直接把 HiCache 移植到手机或端侧设备？

回答：

HiCache 的控制机制可以复用，但它的数据通路依赖服务器环境，例如 CUDA kernel、pinned memory、RDMA 或分布式 L3。端侧的 NPU/GPU 运行时、统一内存和 UFS 接口不同，所以必须重写数据搬运和同步实现。

### 3. 端侧是统一内存，为什么还要区分 L1 和 L2？

回答：

这里首先是逻辑层级，不一定对应两块物理内存。L1 指当前运行时可以直接消费、布局和精度已经就绪的 KV；L2 指仍需映射、复制或格式转换后才能消费的温缓存。层级由可见性、格式、容量和运行时状态共同决定。

### 4. HiCache 已经有 256-token 阈值和 timeout，为什么还需要新算法？

回答：

固定阈值和按 token 数计算的 timeout 没有直接使用端侧实时带宽、Decode 干扰、能量、温度和 UFS 长尾。同样的 256 token 在设备空闲时可能值得读取，在总线拥塞或热节流时可能不值得。EAHS 的目标是在线估计收益，而不是永久使用同一个规则。

### 5. 怎样判断“加载比重算更便宜”？

回答：

先通过 microbenchmark 测量重算时间 \(C\)、加载完成时间 \(R\)、前台干扰 \(I\) 和能耗 \(E\)，再计算读收益 \(U_r=pC-R-\lambda_EE-\lambda_II\)。只有收益为正并且能在 deadline 前完成时才读取。模型参数通过滑动窗口在线更新。

### 6. 复用概率 \(p\) 怎么估计？

回答：

需求加载时 \(p=1\)。预测性预取或写回时，可以先使用低成本特征：会话是否仍活跃、近期访问次数、指数衰减热度、前缀长度、请求类型和复用间隔。第一版使用规则或逻辑回归即可，避免预测器自身开销过大。

### 7. 怎样保证复用的 KV 正确？

回答：

缓存 key 必须绑定模型 ID 和版本、tokenizer 哈希、位置编码配置、KV 精度、page layout 和 token 序列。只复用最长连续、完全兼容的前缀。模型更新、用户登出或配置变化时必须失效和清理。

### 8. 为什么连续前缀很重要？

回答：

注意力需要从序列起点开始的完整历史。一个后缀 page 即使单独命中，只要前面的 page 没有就绪，就不能直接成为可消费的 KV。调度器应从最长连续前缀边界向后扩展，而不是挑选离散高分 page。

### 9. 如果预取到一半 deadline 到了怎么办？

回答：

只采用已经形成连续前缀的部分，其余 page 取消并重算。EAHS 必须支持部分采用、取消和状态回收，而不是全有或全无地等待。

### 10. page size 如何选择？

回答：

page 太小会增加元数据、队列和小块 I/O 开销；page 太大又会增加无效预取和尾延迟。需要在目标设备上扫描多个 page size，比较固定开销、有效带宽、无效字节和取消成本，选择 break-even 区域最稳定的粒度。

### 11. 为什么第一版不同时加入 KV 量化？

回答：

量化解决每 token 占多少字节，分层调度解决哪些历史常驻、哪些低成本恢复。二者是正交变量。如果第一版同时改变精度和调度，很难判断收益来自哪里。因此先固定精确 KV 验证调度，再把 INT8/INT4 作为扩展和消融。

### 12. 目标平台准备选什么？

回答：

先按接口可用性选择。Jetson/CUDA 较接近 HiCache 的异步流机制；Android 可考虑 MLC 或 llama.cpp 钩子；Ascend/MindIE 需要先确认是否能暴露 KV page、异步 load/store 和 phase。最终平台应由实验室硬件和可插桩程度决定。

### 13. 如何测前台干扰、能耗和温度？

回答：

对 Prefill、Decode 和空闲 phase 分别比较无后台 I/O 与不同带宽、队列深度下的 TTFT、ITL slowdown。能耗使用平台可用的功率或电池统计，温度和频率用于判断热节流。所有指标都按时间窗口更新，并报告温度轨迹。

### 14. 闪存磨损怎样量化？

回答：

第一阶段使用逻辑写入字节、写入次数和合并率作为代理指标。若平台能提供更底层统计，再加入物理写放大或健康信息。算法中采用写入预算约束，不声称精确预测闪存寿命。

### 15. 如果实验发现没有收益怎么办？

回答：

这条路线本身设置了止损条件。如果真实 workload 中大多数场景满足 \(R\ge C\)，说明本地持久 KV 的收益空间不足，应及时转向 KV 量化、端云 KV 加载—本地重算选择，或只研究 L1/L2 的小范围调度。明确否定和有效边界同样是研究成果。

### 16. 与 Mooncake、SparKV、Bidaw、KIVI 有什么区别？

回答：

Mooncake 主要是服务器集群的跨实例 KV 复用；SparKV 偏向端侧从云端加载 KV 与本地重算的选择；Bidaw 研究 Host-SSD 分层；KIVI 研究 KV 量化。本课题候选边界是单端本地持久前缀、统一内存前台干扰和读写联合调度。需要在后续检索中进一步确认是否有高度重合工作。

### 17. 为什么 TTFT 之外还必须看 ITL？

回答：

分层缓存主要试图降低 TTFT，但后台读写会抢占 Decode 所需内存带宽。如果只看 TTFT，可能出现首 token 更快、后续生成更卡的情况。因此 ITL 必须是硬约束或目标函数中的惩罚项。

### 18. 最先做的实验是什么？

回答：

最先测四条曲线：不同前缀长度的 Prefill 重算时间 \(C(k)\)，不同 page size 的加载时间 \(R(b)\)，后台 I/O 对各 phase 的干扰 \(I(b,phase)\)，以及能耗 \(E(b,phase)\)。第一张关键结果应是 break-even 区域图，而不是直接实现复杂调度器。

## 四、临场表达注意事项

- 不说“HiCache 已经支持端侧”，说“HiCache 提供了可借鉴的服务器控制机制”。
- 不说“预取一定降低 TTFT”，说“当避免重算大于加载和干扰，并能赶上 deadline 时才有收益”。
- 不说“EAHS 已经有效”，说“EAHS 是拟验证的算法”。
- 不说“128K 上下文一定需要 16 GiB”，说“在给定 8B GQA、FP16 KV 示例下约为 16 GiB”。
- 不使用“首次”或“完全空白”，使用“候选创新点”“拟验证的研究缺口”。
- 被问到未知平台接口时，直接说“需要用第一阶段接口调研确认”，不要现场猜测。
